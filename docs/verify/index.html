Verify an erasure certificate or audit bundle

Paste or drop a file made by inspeximus's erasure_certificate() or audit_bundle(). The page checks it in your browser and shows VALID or INVALID with the reason. Nothing is uploaded: the page's security policy blocks all network requests, and it makes none after loading.

Your file is read locally with the File API.

Try it

What this checks

The page runs the same checks as the command-line verifiers, with no options:

inspeximus erasure-verify certificate.json
inspeximus audit-verify bundle.json

For a certificate it re-derives every tombstone hash from genesis and checks each Ed25519 signature. It checks the anchor's tip, count, RFC 6962 Merkle root and sth_hash, and re-derives the summary (erased_memory_ids, count, request_ids) from the chain. It also confirms the scope statement is the one the library issues and that the certificate covers at least one erasure. For an audit bundle it checks bundle_hash, re-walks both chains, re-derives the anchor's hashes and roots, checks every signature against the key the entry names, and runs the governance, coverage and access-control consistency checks.

Hashes use Python's json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False) encoded as UTF-8, rebuilt byte for byte here, including Python's float formatting and code-point key order. Signatures are Ed25519 over the 32 raw bytes of each entry's SHA-256 hash.

What it does not check

  • That the records are gone from the store. Run the CLI with --store store.json.
  • Whose key signed it. Signatures are checked against the key the file carries, which proves the signer held a key pair, not which one. Pin the key you got out of band with --expected-pubkey.
  • An anchor or witness you trust. --expected-anchor, --witnesses and --require-signed are CLI-only. Without them, anyone can remove the newest tombstones and recompute the anchor, with no key at all, and the shorter certificate still verifies. Whoever holds the signing key can also rewrite and re-sign the whole history.

When the page cannot reproduce the Python verifier exactly, it says CANNOT VERIFY HERE and never INVALID. That covers: a browser without Ed25519, and a signature over a small-order or mixed-order Ed25519 point that OpenSSL (which the CLI uses) would accept but a browser may not. It also covers text Python rejects before verifying (a byte-order mark, invalid UTF-8, an unpaired surrogate, an integer longer than 4300 digits) and fields whose types would make the Python verifier stop with an error. Use the CLI for those. If another check has already failed, the answer is INVALID either way, and the page says so.

Browser support

Hashing uses WebCrypto SHA-256, which every current browser has. Signatures need WebCrypto Ed25519, available from:

Source: MDN browser compatibility data (@mdn/browser-compat-data 8.1.2, api.SubtleCrypto.verify.ed25519 and importKey.ed25519), checked 2026-09-24. The Opera, WebView and Samsung Internet rows are MDN's Chrome figure mapped to that browser's first release on Chromium 137 or later. On an older browser, an unsigned file still verifies.
